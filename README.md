# Fed Liquidity Plumbing

**For education only. Not financial advice.** Figures come from public government sources and are checked, but may contain errors. Check the original source before relying on it.

A one-page dashboard of the Federal Reserve's balance sheet and the overnight money markets: bank reserves, the Treasury's account, reverse repo, net liquidity, SOFR and fed funds against interest on reserves, standing repo use and the Fed's administered rates. The page is `index.html`, served by GitHub Pages.

## Sources

| Data | Primary | Second read / ties |
|---|---|---|
| Reserves, TGA, reverse repo, loans, securities (weekly) | Fed H.4.1 release page, Tables 1 and 5 | The release's own XML file (`FRB_h41_xml.zip`) must equal the page for every row; week-average change = this week − last week; reverse repo = foreign + others; TGA Wednesday = DTS close; reverse repo Others and repo Wednesday = NY Fed operations (repo: every Repo operation outstanding at the end of the Wednesday, settlement ≤ Wednesday < maturity, any term) |
| Treasury account, daily | Treasury Fiscal Data, Daily Treasury Statement | — |
| SOFR, EFFR, target range | New York Fed Markets API (date-range search) | Target range checked against the FOMC implementation note when it changes |
| Standing repo and reverse repo usage and rates | New York Fed operation results (date-range search); usage counts overnight operations only, and any non-overnight operation is listed in the run summary | Wednesday amounts tie to H.4.1 |
| IORB | Fed policy rates file (`FRB_PRATES_xml.zip`) | FOMC implementation note when a rate changes; `lo < IORB ≤ hi`, `rrp ≤ lo`, `srf ≥ hi` |
| Bill purchases | New York Fed Treasury purchase schedule (strict sentence patterns) | — |
| Core PCE | BEA API, table T20804 | — |
| Calendar | H.4.1 every Thursday (next business day after a holiday), FOMC calendar, BEA release dates, month- and quarter-ends, end of the purchase period | — |

FRED is not used. `tests/fixtures/README.md` lists the layout of every file as printed before its parser was written.

## How the update works

Every number on the page comes from nine one-line JavaScript objects between the `// ===== DATA BLOCKS` markers in `index.html`. The script writes seven of them (`DATA`, `WEEKS`, `RATES`, `OPS`, `POLICY`, `CAL`, `LOG`). `NOTES` and `AUDIT` are written by hand and never touched. The script writes numbers, dates and short check-log strings; every sentence on the page is generated by the page's own code.

`.github/workflows/update.yml` runs `scripts/update.py` on weekdays at 14:40, 22:15 and 01:15 UTC. The script is plain Python with no AI. It fetches each source (browser User-Agent, 60 s timeout, retries after 5, 15 and 45 s), maps fields by exact label (repeating labels such as `Others` are matched only inside their parent row's block), rewrites the seven lines and runs the checks:

1. Two reads: H.4.1 HTML and XML agree on every value used for the newest week. If the XML cannot be read, the H.4.1 rows are logged as single source.
2. Ties (listed in the table above).
3. Seed check (first run per source, while its log row says "Seeded"): values re-read for a date the page already holds must equal the page — all 17 `WEEKS` rows from their dated releases, the `DATA.h41` week, `RATES` and `OPS` for every seeded date, `POLICY`, the DTS close and core PCE. Any difference stops the run and lists it.
4. Moves over 5% (10bp for rates; amounts under $5B exempt) go into the run summary and the commit message; reserves, assets or net liquidity moving more than 5% in a week, or the TGA more than 15% (it swings 5–10% a week around tax dates), also opens an issue.
5. Only the seven data lines changed; `NOTES` and `AUDIT` are byte-identical.
6. Array lengths (17 weeks, 10 business days) and date order; no weekends or holidays.
7. The page script parses (`node --check`) and Node reads the blocks back unchanged.

A source with nothing new keeps its old value and date. When a `RATES` or `OPS` date exists because one series has it while the other series has not published that date yet (SOFR posts about 8:00 am ET, EFFR about 9:00 am), the missing cell is a `null` placeholder: not a failed read, no issue, logged as "Not published yet", listed in the run summary, and filled by the next run, which re-reads the last 10 dates of both series. A placeholder never replaces a value the page already holds. `DATA.dts` holds one date, so a DTS not posted yet simply keeps the old date and value. A source that shows a newer date but whose value cannot be read or fails a check gets `null` under the new date, a log row saying so, and an issue. A failed check on a date the page already holds keeps the page value. The script also writes `data/summary.json` for other pages.

The workflow commits only when a data value changed and every check passed, using the repository variables `COMMIT_NAME` and `COMMIT_EMAIL`. If a check fails, nothing is committed, the run fails, and an issue titled "Data update needs attention" is opened or commented on.

### Alerts

Alert issues (`scripts/alerts.py`) and the "Data update needs attention" issue are assigned to the repository owner, read from `GITHUB_REPOSITORY_OWNER` at run time; being assigned subscribes the owner, so GitHub emails each new issue and comment. Alert issues carry the label `alert`:

| Alert | When |
|---|---|
| `Alert: <tile> turned <label> (<data date>)` | A tile's status differs from the previous `data/summary.json` (both known). New issue each time. |
| `Alert: Fed policy change (<date>)` | The target range, IORB, standing repo or reverse repo rate changed, or a new purchase period changed reserve management purchases. New issue each time. |
| `Alert: SOFR above IORB`, `Alert: EFFR above IORB`, `Alert: Standing repo usage above $25B` | One open issue; a comment on each new day above; closed with a comment when back under. |
| `Alert: Reserves moved <±$xB> in week of <date>` | The week-average change in reserves exceeds $100B. New issue each time. |
| `Data update needs attention` | A failed check, a null, or a source that could not be parsed. |

### Manual run

Actions → Update data → Run workflow. `dry_run` defaults to true: the run fetches, parses and checks, then writes to the run's Summary page every value that would change (old → new, "added" for new points, data date, source), the moves, the alerts that would open, the sources not reached and any label a parser could not find. It commits nothing and opens nothing. `skip_seed_checks` accepts source values that differ from the seeded page values; use it only after reviewing a dry run.

Locally:

```
pip install -r requirements.txt
python -m pytest tests
python scripts/update.py --dry-run
```

### Repository settings

- Secret: `BEA_API_KEY`.
- Variables: `COMMIT_NAME`, `COMMIT_EMAIL` (the GitHub no-reply address) for the commit author.
- Pages: deploy from the default branch, root folder.
- Network: `www.federalreserve.gov`, `markets.newyorkfed.org`, `www.newyorkfed.org`, `api.fiscaldata.treasury.gov`, `apps.bea.gov`.

## Not automated

The `NOTES` block (causes, decisions, what banks expect), the explanatory text on the page (audited by hand monthly; `AUDIT` holds the dates), and judgment about whether a day above IORB is calendar noise or a signal.
